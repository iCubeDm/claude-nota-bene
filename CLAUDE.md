# Nota Bene

A browser IDE over Claude Code: the chat with the agent, inline margin comments on any reply or file (sent as one batch), file tree, media viewer, sessions. Built on the Claude Agent SDK.

## Layout

- Root: the app (React + TypeScript), npm workspaces `shared/`, `server/`, `web/`, plus `e2e/`, `bin/nota-bene.mjs` (launcher), `plugin/` (the Claude Code plugin: `plugin/skills/nb/` is the `/nb` skill, `plugin/.claude-plugin/plugin.json`) and `.claude-plugin/marketplace.json` (the marketplace that lists it).
- `docs/` — notes, specs, plans, the draft feedback to Anthropic.

The local root compat symlinks (`server.mjs`, `public`, `ide.sh`, `skill`, `.sessions.json`) were removed at the M5 switch-over on 2026-10-26; `~/.claude/skills/nb` points at `plugin/skills/nb/` (one copy serves the checkout link and the plugin).

## Rebuild (root)

Node >= 23.6 (the server runs `.ts` directly). From the repo root:

- `/nb`, `/nb new`, `/nb fork` — from Claude Code, via `plugin/skills/nb/` (linked with `ln -sfn "$PWD/plugin/skills/nb" ~/.claude/skills/nb`, or installed as the plugin): open the window for the caller's folder; resume its last session / start fresh / continue this conversation as a branch. The skill runs `open.sh --data '${CLAUDE_PLUGIN_DATA}' --plan` (single-quoted: a live `${...}` makes Claude Code refuse the line) (guards, the "already open" check; it launches nothing and prints `NB-RUN` / `NB-WAIT` / `NB-NAME`), then runs the foreground launcher as a Claude Code background task (it shows in the session's task list, its output is the window's log; stopping the task, or ending the Claude Code session, stops the window), then `open.sh --wait` (polls `--find` up to 40 s) for the URL. `open.sh` finds the launcher in this order: a checkout (`bin/nota-bene.mjs` three levels above the physical skill dir, Node >= 23.6); else the npm package `nota-bene-ide@<plugin version>` under the plugin data dir (`${CLAUDE_PLUGIN_DATA}` is not in the env of Bash commands, so SKILL.md passes it as `--data`; Node >= 22). The first run installs it with `npm install --prefix <data>` inside NB-RUN (`open.sh --run`, in the background task, never in the `--plan` preprocessing; the plan adds an `NB-NOTE:` line and `--wait` waits for the install up to 540 s, `NB_INSTALL_WAIT_SECS` for tests); one install per version in `<data>/<version>/` (about 330 MB each, not pruned yet); `.nb-installed` there (written last) tells it is done, `.nb-install-failed` makes `--wait` report a failure at once, and `--wait` also reports at once an install whose lock holds a dead pid, or that never started. Once installed, NB-RUN is plain `node <data>/<version>/node_modules/nota-bene-ide/bin/nota-bene.mjs ...`. The commands in the plan are built by `q()`: safe words as they are, anything else single-quoted (Claude Code refuses backslash-escaped spaces and `$'\320...'` escapes). The plugin version must equal the root `package.json` version (a test checks it) and `plugin/` must hold no `package.json` or lockfile (Claude Code would run its own npm install there). Test: `scripts/nb-open.test.ts` (kept out of `plugin/`, which ships to users).
- `node bin/nota-bene.mjs [dir] [--port N] [--resume ID [--fork]] [--new] [--detach] [--no-open]` — the launcher the skill uses. It rebuilds a stale `web/dist`, then opens the browser (`--no-open` skips that). One window per folder (a launch takes the folder's lock and gives way to a window already serving it, waiting up to 10 s for one in its restart gap). It supervises the server: exit 75 relaunches at once with `--continue`; 0, 130, 143 exit; anything else is a crash, relaunched after 1 s, giving up at 5 crashes within 60 s. A relaunch keeps the port and the registry entry (no other launch takes the port meanwhile); a 98 on a relaunch gives up at once. `--detach` prints one line (`opened URL` or `already-open URL`, the URL with the `#t=` login fragment) and leaves the window running on its own (terminal use; its log is `$TMPDIR/nota-bene-PORT.log`). Without `--detach` it runs in the foreground: the server's `Nota Bene: URL  project: DIR` line is its first output after any build, Ctrl-C (SIGINT) or SIGTERM stops the server and unregisters the window. The server watches its parent (`NOTA_BENE_LAUNCHER_PID` vs `process.ppid`, every 2 s) and exits when the launcher is gone, so a SIGKILLed launcher leaves no orphan; a foreground launcher likewise stops (as on SIGTERM) when its parent shell is gone (not a `--detach` child, nor one started with ppid 1).
- `node bin/nota-bene.mjs --find DIR [--scan]` prints the port of the live window serving DIR (exit 1 if none; `--scan` also asks the other ports of the range, for a window whose registry write was lost); `node bin/nota-bene.mjs --last DIR` prints DIR's last session id if its transcript still exists (exit 1 otherwise); `--url PORT` prints the window's login URL, `--front PORT` brings it to front logged in (see Access token). All are the skill's helpers.
- `npm start [-- <dir> --port N --resume ID --continue]` — builds `web/dist`, then serves app + API from the server directly, unsupervised (default port 4777; project = the directory you ran npm from, or the `<dir>` argument, relative to it).
- `npm run dev` — (login: `npm run dev:open`, see Access token) server on 4780 (`node --watch`, with `--allow-origin http://localhost:5173`) + Vite on 5173 (proxies `/info` and `/ws` to the server). Open http://localhost:5173. Dev has its own state dir, `~/.nota-bene-dev` (set `NOTA_BENE_HOME` to override), so experiments never touch the working `~/.nota-bene`; the server logs `state: <dir>` at startup.
- `npm test` — unit tests (vitest, ports are 0 / random).
- `npm run e2e` — Playwright, ports 4791-4795. The `files` project uses `ffmpeg` on PATH to generate its media fixtures at startup; without it the media tests are skipped with a message (`NB_E2E_FFMPEG=0` forces that path).

- `node scripts/build-package.mjs [--out DIR]` — builds the publishable npm package into `pkg/` (git-ignored; never publishes): esbuild bundles `server/src/main.ts` and `bin/nota-bene.mjs` to plain JS at the same depth (`server/src/main.js`, `bin/nota-bene.mjs`; `@nota-bene/shared` inlined, `ws` and the Agent SDK external), a FRESH `web/dist` (own outDir, emptied; the local `web/dist` keeps its old chunks), the two blend assets, LICENSE, README and a generated `package.json`. The name (`PACKAGE_NAME`, now `nota-bene-ide`; the command is `nota-bene`) and the Node floor live as constants in that script; the version is the root `package.json` `version` (the root stays `private`). Installed, there is no `web/src`: the launcher never builds, `/info.codeChanged` is false (no `.ts`), About reads the package version, and nothing is written next to the code (state is in `NOTA_BENE_HOME`). Test: `bin/package.test.ts`.

Experimental 3D (the model tab for `.glb` `.gltf` `.blend`, Blender): off by default, on with env `NOTA_BENE_EXPERIMENTAL_3D=1` on the server. Off: `/model` is a 404, Blender is never looked up (`/info.blender` false), `hello.capabilities.model3d` is false, and the web treats model files as any other unsupported file (text kind, generic icon) and never fetches the three chunks. The e2e `files` fixture runs with it on; the `controls` fixture keeps it off (`e2e/model3d-off.spec.ts`).

Ports: launcher windows may sit anywhere in 4777-4799 except 4780 and 4790-4795; dev 4780 (server) and 5173 (Vite); tests use only 4790-4795 (manual smoke 4790, unit/e2e 4791-4795), never another port. `/info.root` tells windows apart.

State lives in `~/.nota-bene/` (override with `NOTA_BENE_HOME`), never in the repo:

- `token` — the local access token (32 random bytes as hex, mode 600, state dir 700; see Access token below). Deleting it rotates it at the next server start. `control-token` is the separate secret of the cross-window `/control/` routes
- `open/` — the pages the launcher opens the browser on (mode 600, dir 700; each holds the login URL of one launch, which dies with that launch; same trust as `token`). Removed 30 s after by the launcher if it is still running; a page left by a launcher that exited stays until the next page is written more than 10 minutes later (the next sweep)
- `sessions.json` — the last session per project (folder)
- `prefs.json` — agent permission mode per project dir (`modes[root]`)
- `comments/<sessionId>.json` — pending and sent margin comments of one agent session
- `attachments/<sha256>.<ext>` — pasted images, content-addressed; only ids travel over the socket
- `windows/<port>.json` — the window registry (`root`, `pid`, `launcherPid`, `startedAt`)
- `locks/<hash>` — per-folder launch locks
- `history/<sessionId>.jsonl` — the archive of the conversation before each compaction, one line per segment (the SDK replays a session only from its last compaction)
- `cache/blend/<key>-<blender version>.glb` (key = sha256 of the file bytes + its root + its folder) — `.blend` files converted to GLB for the model tab (re-creatable; safe to delete)
- `trash/` — `attachments/` and `history/` subfolders: what Settings → Storage "clean" moved (never deleted)

## Access token

Nothing on the machine reaches the API or the socket without a secret (`server/src/auth.ts`). The server listens on 127.0.0.1 only, but any local process or other OS user could connect, so an unset `Origin` is accepted only with valid auth.

- The secret is `<NOTA_BENE_HOME>/token`, created on first need with an exclusive link (two first launches agree). **Only a missing file makes a token (the ssh rule)**: a loose mode (group/other readable), garbage content, a foreign owner, a directory, a FIFO or a symlink (opened with `O_NOFOLLOW|O_NONBLOCK`) make the server and every helper throw a clear message naming the file and the fix (`chmod 600 <file>`, or delete it to get a new token, which logs every window out). Nothing is rotated silently. A state folder owned by another user is refused. The same rule holds for `control-token`, which is made at server start, never by a request. The secret never goes in argv, in the environment of the agent or of `!` commands (the server reads the file), or in a log. The startup line, `/info` and `$TMPDIR/nota-bene-PORT.log` (created 600, `O_NOFOLLOW`) do not print it.
- Browser: the window is opened on `http://127.0.0.1:PORT/#t=<login>`, where `<login>` = HMAC(token, `nota-bene:login:<port>:<nonce>`): **never the raw token**, so a URL that leaked opens that one window and dies when its launcher exits (a URL from `--url` lasts until then; after a crash relaunch or a new launch it is dead). The page (`web/src/net/auth.ts`) takes the fragment out of the address bar first, then POSTs `{login}` to `/auth` (same-origin, JSON; the raw token is refused there) and gets `Set-Cookie: nb_<port>=<cookie credential>; HttpOnly; SameSite=Strict; Path=/; Max-Age=1 year` plus the page's **key** in the JSON body, which it keeps in localStorage (`nb.key`; origin-scoped, port included).
- Per-launch nonce: the launcher makes a random nonce and hands it to every server it starts (env `NOTA_BENE_NONCE`). **Exit 75 (the user's restart) keeps it, so open tabs stay logged in; a crash relaunch takes a new one and the launcher opens a fresh login page**, so whatever the crashed launch handed out is dead and the user is logged in again. An unsupervised server makes its own; `npm run dev` makes one for the whole session (`scripts/dev.mjs`), so a `node --watch` reload does not log the page out. It is public, not a secret, and still stripped from the server's own env after reading and from `shellEnv`. Every derived value is HMAC(token, `nota-bene:<label>:<port>:<nonce>`) with its own label (`cookie`, `key`, `helper`, `login`; `proof` adds the challenge): a value captured in one launch is dead in the next, and one captured for a port is dead on any other. Tabs of the old launch show the overlay. A second tab, a reload and `Restart the server` keep working.
- Two tiers. The cookie alone opens **only `GET`/`HEAD` of `/file` and `/attach/<id>`** (what `<img>`, `<video>`, `<audio>` and a 3D loader's textures load with no way to add a header; `cookieRoute` in `auth.ts`). `/model` is not among them: its loader is a `fetch`, so it goes through `apiFetch` and needs the key. **Every other route needs the key as well, `/info`, `/tree`, `/sessions`, `/complete`, `/system/*` and the socket included, and so does any route added later (key tier by default; `server/src/auth.test.ts` pins every route in a table).** The key travels as the header `x-nota-bene-key` through the one `apiFetch` helper in `web/src/net/auth.ts` (every `fetch` in `web/src` but `/file` and `/attach` uses it), and the socket offers it as the `nb.<key>` subprotocol, echoed by the server, never in the URL. Helpers send `Authorization: Bearer <helper credential>`; that and the raw token as Bearer (a script of the user's own) open everything. A cookie without the key gets 401 on the socket and everywhere but `/file` and `/attach`, with no frames; a page whose key is gone (cleared storage) gets the 401 from `/info` and shows the overlay.
- No derived value goes to a port that has not proved itself: **helpers first ask the public `GET /hello?c=<random hex, 16-64>`**, which answers only `{proof, n}` (proof = HMAC(token, `nota-bene:proof:<port>:<n>:<c>`) for the port the server is bound to; no root, no state; a malformed `c` is 400). `proveListener` / `verifiedBearer` (`auth.ts`) pick a fresh `c`, check the proof in constant time against the port they dialled, and only then derive the helper bearer from the `n` of the checked proof. A bad or missing proof means "not ours": nothing is sent, no retry. Every probe goes through it: `probeInfo` (`--find`, `--find --scan`, the launcher's liveness checks, `--detach`), `probeWindow` and the control relay (Settings → Windows), and `--url` / `--front`, which also refuse any URL whose listener did not prove itself, because the login URL carries the raw token in its fragment where the page's own script can read it. `--front http://localhost:N` / `--url http://localhost:N` are the dev page: the backend (4780) must prove itself directly and so must `localhost:N` through the Vite proxy (`/hello` is proxied; the proof is bound to 4780). A program that relays `/hello` to the real backend would still pass; that is what a proxy is, and it is dev only.
- Protected: every route and `/ws` (401; the socket is refused at the handshake, before any event; the socket server upgrades `/ws` only). Public: `/`, the static assets, `/auth` (POST, own-Origin only) and `/hello` (the proof, below). The Host and Origin checks stay in front: a non-GET request needs an Origin from the allowlist **even with a Bearer** (a script sets `Origin: http://127.0.0.1:PORT` itself; without one the answer is 403), and `/ws` accepts an unset Origin only with valid auth. `/control/` is the exception: its own token (`control-token`), and any Origin is refused. Compare in constant time.
- The launcher opens the browser on a mode-600 page in `<state>/open/` that redirects to the login URL (so the token is not in `ps`; the page stays until the next sweep, see the state list). `--detach`'s `opened URL` / `already-open URL` and `nota-bene --url PORT` carry the `#t=` fragment (the user's own terminal: a second browser can log in with it); the foreground `already open at` line, every log and **everything the `/nb` skill prints** do not — the skill's `NB: opened URL` / `already open at URL` are plain URLs, because its output enters the Claude Code transcript and goes to the API. A browser logs in through the redirect page: the launcher opens it for a new window, and `open.sh` calls `--front` for one already open. Helpers: `nota-bene --url PORT` (the login URL), `--front PORT` (bring to front, logged in), `--find DIR --scan` (also asks the other ports of the range, which replaced the skill's bare `curl`). 
- A page without a login (a bookmark, a copied address, a tab of an earlier launch) shows the overlay "This window is not logged in" (en/ru) and stops reconnecting: a socket that closes before its first frame is checked with `GET /info` (with the key), and a 401 there ends the retries. A server restart (exit 75) and an open tab keep working (the nonce is kept).
- `startServer` takes the test-only `insecureNoAuth`; `main.ts` and the launcher never set it and there is no flag or env var for it. Unit tests that are not about auth pass it; `server/src/auth.test.ts` and `e2e/auth.spec.ts` run with auth on. The e2e servers are seeded with a known token and nonce (`e2e/serve.mjs`), and `e2e/playwright.config.ts` gives every project the matching cookie and localStorage key as its storage state (`e2e/auth.ts`).
- Trust limit: the token file is readable by the same OS user, so the user's own agent (and anything else running as that user) can read it. That is accepted: the aim is to keep out other users and other local software that cannot read the file, not the user's own tools. **File routes never serve the state folder**: `/file`, `/tree`, `/model`, `/complete` and every `src=` source (live worktrees and git blobs) refuse, list and search nothing whose real path is the state folder or inside it (`server/src/stateGuard.ts`), so a root that contains it (a session in `$HOME`) does not hand the token to a cookie. Residual risk, accepted for v1.0: browsers send cookies to every port on 127.0.0.1, so while a window is live a local web server the user visits sees its `nb_<port>` cookie, which reads files in the project through `/file` and pasted images through `/attach/<id>` (a GET of a pasted image id also restores it from the trash), nothing else, and cannot open the socket or write (the key is in localStorage, which no other origin reads); it is dead after the next launch. Rotating everything means deleting `<state>/token` and restarting the server: a window that is live under the old token can no longer be proved by the helpers, so it has to be reopened (`--find` does not see it, and a `/nb` or launch meanwhile starts a second window on the folder). A token that was ever committed to git stays readable through `.git/objects` even after the file is removed from the tree; the state folder is not a place for a repository, and the file guard (`stateGuard`) only covers the working tree and the branch reads.
- `/file` serves `.html` and the other text kinds as `text/plain` and everything under a CSP `sandbox` (opaque origin, so cross-site for cookies): a sandboxed document that loads a subresource from `/file?...` gets no cookie and so a 401. Only a top-level opened `.svg` with absolute `/file?` references is affected (the app never frames `/file`; `<img src="/file?...svg">` and media are same-origin loads and carry the cookie). The auth on `/file` was left alone.
- Dev: `npm run dev` has its own state dir and so its own token; `npm run dev:open` opens `http://localhost:5173` logged in (the Vite proxy forwards `/auth` and `/hello`, the cookie is `nb_4780`; it refuses to hand the token to a listener on 5173 that cannot prove itself). Upgrading: a window started before this version has no `/hello`, so the new helpers take it for dead (`--find` misses it, Settings → Windows lists it as silent) until it is relaunched.
- Smoke on 4790 (manual): with a temp `NOTA_BENE_HOME` the server creates `token` at start. Log a browser in with `node bin/nota-bene.mjs --front 4790` (or print the URL with `--url 4790`), both with the same `NOTA_BENE_HOME`: they ask the window for its proof first. For the API use the raw token as a Bearer in your own shell: `curl -H "Authorization: Bearer $(cat "$NOTA_BENE_HOME/token")" http://127.0.0.1:4790/info`. Without a credential every route but `/`, `/auth` and `/hello` answers 401.

Server routes besides the app (all behind the access token above except `/auth`): `/auth` (POST the token, public: sets the login cookie), `/info`, `/ws`, `/tree`, `/file` (Range; sandboxed headers), `/complete` (`@` search), `/attach` (POST image, GET `/attach/<id>`), `/sources` (this checkout, other worktrees and branches; read-only, `src=` on `/tree` `/file` `/complete`), `/sessions` (all Claude Code sessions with their cwd, for the picker), `/history?session=&before=` (one archived segment; 409 for a session that is not the current conversation, 404 when there is none), `/subagent?session=&tool=<toolUseId>` (a subagent's conversation as feed events, `{events, running, type, description}`; 409 for a session that is not the current conversation, 404 when no subagent matches, 400 for ids that are not plain ids; the web opens it as an `agent:<toolUseId>` tab, read-only, polled while it runs), `/task-output?session=&task=<taskId>` (protocol 8: the tail of a background shell / Monitor task's output, `{output, totalBytes, truncated, running}`; same 400 / 409 / 404 rules, 404 also for a task that is not a shell one; the web opens it as a `shell:<taskId>` tab, polled every second while it runs). `/model?path=&src=` (a `.blend` converted to `model/gltf-binary` by the local Blender: `NOTA_BENE_BLENDER`, else `blender` on PATH, else `/Applications/Blender.app/Contents/MacOS/Blender`; always `-b --disable-autoexec --factory-startup`, paths as argv, never in Python source; a .blend that references files outside the project (or has a Geometry Nodes import node / disk bake) is refused with 422 `outside-refs`; on macOS Blender also runs under `sandbox-exec` (`server/src/blend/sandbox.sb`: reads only the project root, the Blender install and the system; writes only its work dir; no network); one conversion at a time, 120 s timeout → 504, no Blender → 501, failed export → 422; `/info.blender` says whether one is found). Protocol 10: the server event `commands` (the slash menu's list, never stored, sent to every new socket with the other state, replaced whenever the agent pushes `commands_changed`, emptied by a session switch). The Claude backend offers every non-`builtin` command or skill plus the built-ins in `server/src/agent/claude/commands.ts` (`BUILTIN_OK`, each tried against a real CLI), never one the CLI tags `terminal_slash_commands`; the composer's `SlashPicker` shows it for a `/` at offset 0, up to the first whitespace. `system/local_command_output` is shown as a reply. A `/compact` or `/clear` typed in the composer is tracked like the buttons (same `turns` marking). The task indicator under the composer opens the bottom drawer (Alt+T); Stop and To background are the client messages `task-stop {id}` / `task-background {toolUseId}` (protocol 8).

`! cmd` in the composer (protocol 11): a one-line draft that starts with `!` (offset 0, space optional; not `![`) is a shell command, not a message; a draft of several lines is an ordinary message, so a pasted script never runs on one Enter, and a space before `!` sends it as text. Enter / Run sends the client message `shell-run {id, cmd}` (owner socket only, the same validation as every client message: `cmd` a non-empty string of at most 32 KB; no HTTP route). A refusal (one is running; a switch is in progress) is the event `shell-refused {id, reason}` to the asking socket, and the page puts the draft back. The server (`server/src/session/shell.ts`) runs `$SHELL -lc -- cmd` in the current root (`$SHELL` only when its basename is sh, bash, zsh, dash or ksh, else `/bin/sh`: a fish user gets `/bin/sh` for `!`, because `-lc --` is untested there; the `--` keeps `! --version` a command), stdin `/dev/null`, in its own process group. The environment is ours minus the launcher's variables (`NOTA_BENE_SUPERVISED`, `_LAUNCHER_PID`, `_LOCKED`, `_AUTOPORT`), Claude Code's own state (`CLAUDECODE`, `CLAUDE_PID`, `CLAUDE_CODE_*`; `CLAUDE_CONFIG_DIR` stays) and, when npm started the server, npm's leaks (the launcher's `serverEnv` rule; `shellText.ts` `shellEnv`, held together by a test). One command at a time per window; it works while the agent is busy and starts no turn. The feed gets one block: `shell-start` (stored; kept through a compaction while the run goes), `shell-out` (live only; the WHOLE tail so far, ANSI stripped, stdout and stderr merged, replacing what the page shows, at most ten a second and skipped for a socket more than 1 MB behind, so a command that prints without end cannot grow the server; the pipe is always drained; a socket that attaches mid-run gets the tail in one frame), `shell-end` (stored; the last 64 K characters, `truncated`, exit code, `stop` = `user` | `timeout`, `error` when it could not start). `shell-stop {id}` sends TERM to the group, KILL after 3 s (the KILL still comes after the block has ended); the same after 10 minutes (`stop: 'timeout'`). When the shell exits, the rest of its group gets TERM and, 3 s later, KILL (polled every 150 ms: an empty group is not signalled again, its id may be reused; the run stays in the exit hook until then): a background job (`cmd &`) ends with the command. A session switch, a restart, a `/clear` and a server close stop a run quietly (no end event, its output dropped). A process exit hook kills the live group on any normal exit, and `main.ts` turns SIGINT, SIGTERM, SIGHUP and SIGQUIT into a close; only a SIGKILL of the server itself leaves a running command behind (no watcher process). No pty: an interactive command (an editor, a pager, a password prompt) gets EOF and ends on its own, usually with a non-zero code; the block shows no hint.
The agent hears of finished runs with its next message, no extra turn: at the moment the text is handed to the agent the server puts them in front of it in Claude Code's own form (checked against its transcripts: `<bash-input>cmd</bash-input>`, then `<bash-stdout>…</bash-stdout><bash-stderr>…</bash-stderr>`; a silent run is `(Bash completed with no output)`; stdout and stderr stay separate, 32 K characters each, a cut marked; `</bash-` in a command or its output is written `<\/bash-` so output cannot close a tag; a stopped run or a non-zero exit adds a line to stderr; the whole lead is at most 64 K characters, the oldest runs left out with a note after the blocks (a replay drops it), the newest always in; at most 10 runs wait). A failed hand-over puts the runs back (not for a `/clear`: they are dropped as it is accepted, a failure there loses them). A message that is a slash command (`/compact`, `/clear`, a skill) goes out as is and the runs wait for the next one (a `/clear` drops them when it is handed over, so the message behind it starts clean). The queue survives the agent's in-process restart, and is dropped on a switch to another session and on a `/clear`. The feed shows the message as typed, without the blocks; on a transcript replay the exact leading blocks of a user message (also one with images) become shell blocks again (no exit code kept; text a user typed in exactly that form at the start of a message would show as a block too: accepted). The block lives in the hub like other events, so a page reload replays it; a block of a run the agent never heard of (no message since) is lost with a server restart or a ↻, because the transcript holds only what went to the agent.

One tab per window: the first socket owns the session; a second tab gets "Окно уже открыто в другой вкладке" and can take over ("Работать здесь"), after which the old tab gets close code 4001 and shows the overlay too. A reload of the owner within 700 ms is not a second tab. Tests that need several sockets pass `oneTab: false` to `startServer`.

Session switch and ↻ are in-process: the server closes the SDK query and resumes (another) session, possibly re-rooting to another project folder; a new session may only start in the current root or in a folder that already has sessions.

Restart semantics: ↻ restarts the agent, not the server process; it stays available while the agent is busy (escape hatch). The ↻ menu also has "Restart the server", shown only when `/info.supervised` is true (the window runs under the launcher): the server exits with code 75 and the launcher relaunches it with `--continue`, so the session resumes. Under `npm start` / `npm run dev` there is no such item.
