# M4 Session & Agent Controls Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Full prototype parity for the controls around the chat:
- the session picker over all folders, with an in-process switch;
- the session title in the tab and the window title;
- footer meters (context, 5h and week limits, cost);
- compact and clear;
- the plan card;
- the mode pill with Shift+Tab;
- prompt suggestions;
- the state favicon;
- toasts for server errors;
- ↻ restart;
- the background-task line.

After M4 only M5 (launch through `/nb`) stands between the user and the switch from the prototype.

**Architecture:**
- **One `SessionManager` per server owns the agent, and it can now be replaced in-process.**
  - `switch()` and `restart()` close the SDK query and start a new one, with resume, possibly in another project folder.
  - The project root becomes mutable server state, read through `manager.info().root` by every route. Root-dependent pieces are re-created on a root change: file routes, sources, the completion cache, the comment store key.
- **New server state goes to every socket as unstored events**, like `comments`: `stats` and `mode`. `session` grows `title` and `model`.
- **The web adds the slices `controls`, `stats` and `tasks`.** UI-only behaviour (favicon, toasts, suggestions) lives in small hooks.

**Tech Stack:** as M3. No new dependencies.

**Already done before M4:** `--chrome`. `extraArgs: { chrome: null }` is in `server/src/agent/sdk.ts`, so there is no task for it.

**Spec:** `docs/superpowers/specs/2026-10-24-nota-bene-rebuild-design.md`, section "Parity checklist → Session & agent controls (M4)", and the state table (`prefs.json`).

**Reference:** the prototype's behaviour, with exact constants, i18n texts and line numbers, is in the M4 research notes, `docs/superpowers/plans/2026-10-25-m4-research.md`. The prototype itself is `prototype/server.mjs` and `prototype/public/index.html`, read only.

**Base:** branch `m4-controls` from `main`.

## Global Constraints

- The M0–M3 rules still hold:
  - one task = one small commit with What / Why / Verified by and the trailer `Task: M4-NN`;
  - every UI string goes through `t()` in ru and en, with the prototype's texts where it has them;
  - no state in the repo;
  - `prototype/` untouched except for bug fixes;
  - ports: 4790 smoke, 4791–4794 e2e, never 4777–4781.
- The manual smoke uses a temp `NOTA_BENE_HOME` **and** a temp `CLAUDE_JOURNAL_VAULT`.
- Rulings for M4:
  - **R-M4-1.** The switch is in-process, as the spec says. ↻ restarts the **agent** in-process: it closes the query and resumes the same session. Reloading server **code** is a dev concern (`node --watch` in `npm run dev`), and M5's launcher adds a supervised full restart. The ↻ tooltip says what it does.
  - **R-M4-2.** The permission mode is persisted per project dir in `~/.nota-bene/prefs.json` (spec state table), not per port as in the prototype. The default is `'auto'`.
  - **R-M4-3.** Native `confirm()` and `alert()` are not used. All confirmations are a dialog component (shadcn Dialog) with Esc and Enter, following the Esc protocol.
  - **R-M4-4.** The session picker and the compact and clear buttons are disabled while the agent is busy, as in the prototype. The server also rejects `switch` and `command` while busy, with `server-error` `where: 'busy'`. **↻ (`restart`) stays available while busy**, because it is the escape hatch for a stuck agent: it interrupts first, with a 2 s cap, then resumes the same session (ruled during M4-04).
  - **R-M4-5.** Server errors become toasts, deduplicated as ×N with a 15 s timeout that pauses on hover. They are no longer feed notices; M3's `tone: 'error'` notice is removed.
  - **R14 (from M1).** The client → server `comments` message carries `sessionId`. The server rejects a mismatch with the current session, so a set that is in flight during a switch cannot land in the wrong session.
- Prototype constants, verbatim:
  - `MODES = ['default','acceptEdits','plan','auto']`, and Shift+Tab cycles in that order;
  - meter classes `warn` ≥ 60 and `hot` ≥ 85;
  - `fmtK`;
  - the stats refresh 1.5 s after start, every 5 min (limits throttled to 1/min), and after every `result`, `conversation_reset` and `compact_boundary`;
  - `getContextUsage` with a 10 s timeout, and the usage call with a 15 s timeout;
  - `cwdOf` reads the first 256 KB, caches results, nulls included;
  - `listSessions({ limit: 300 })`, dropping entries without a cwd;
  - FAV colours, the 700 ms blink, the state priority wait > work > done > idle;
  - `toast`: dedup key `title\nmsg`, 15 s timeout.

## Review Focus

1. **A switch while things are in flight.** This covers a pending permission card, unsent comments, a comments push in flight (R14), an open file tab of the old root and a playing video.
   - After a switch, nothing from the old session or root shows or is served: the feed, the comments, the tree, the tabs (each root restores its own) and `/file` all follow.
   - Test in M4-04 (server) and M4-16 (e2e).
2. **Two windows on one server.** When one window switches, compacts or clears, the other follows: the replay is reset, the session event and the title update, and its tabs restore for the new root. Test in M4-04 and M4-16.
3. **The mode echo loop.** The UI is optimistic, the server echoes, and the CLI can change the mode by itself (approving a plan drops it to `default`, then we restore the earlier mode). This must never oscillate or send `mode` twice for one click. Test in M4-02 and M4-06.
4. **The experimental usage API is missing, throws or changes shape.** The meters degrade: no limits, cost if known, and the context meter alone. They never crash or log on every tick. `stats` is never stored in the replay. Test in M4-03.
5. **`/clear` while the user has pending comments on chat messages.** The feed is emptied and the old comments stay with the old session; they are not orphaned in the new one. The panel shows the new session's (empty) set and the old session's set comes back when it is reopened from the picker. Test in M4-05 and M4-09.

export const MODES = ['default', 'acceptEdits', 'plan', 'auto'] as const;

### M4-03: Stats service

**Files:**
- Create: `server/src/stats.ts` and its test.
- Modify: `agent/{types,sdk,fake}.ts`, `session.ts`, `server.ts`.

**Interfaces:**
- Produces:
```ts
// AgentSession: contextUsage(): Promise<{ used: number; max: number; pct: number }>
//               usage(): Promise<{ cost: number | null; limits: Stats['limits'] }>   // sdk: usage_EXPERIMENTAL…({skipBehaviors:true}); throws if absent
export class StatsService {
  constructor(o: { session: () => AgentSession | null; emit: (s: Stats) => void; now?: () => number });
  current(): Stats;
  refresh(o?: { limits?: boolean }): Promise<void>;   // context always; limits at most 1/min unless forced
  onSdk(m: SDKMessage): void;                          // result / conversation_reset / compact_boundary → refresh; rate_limit_event → merge
  start(): void; stop(): void;                         // 1.5 s first tick, 5 min interval (unref)
}
```
- Rules, following the prototype's `refreshStats`:
  - Timeouts: 10 s for context and 15 s for usage. A failure keeps the previous value.
  - `rate_limit_event`: when `rateLimitType` is one of `five_hour`/`seven_day` and `utilization != null`, set `pct = u <= 1 ? u*100 : u` and `resets_at = resetsAt ? ISO(resetsAt*1000) : null`. Merge it into `limits`.
  - `stats` is emitted with `{store:false}`. A new socket receives `current()`.
  - An API that is missing or throws produces at most one `server-error` per process, never one per tick.

- [ ] **Step 1: Failing tests (fake timers, stub session).**
  - The context maps from `totalTokens`, `rawMaxTokens || maxTokens` and `percentage`.
  - Limits are throttled to once a minute.
  - A `rate_limit_event` with utilization 0.42 gives 42.
  - A throwing usage API keeps the context and reports once.
  - `stats` is never in the hub history.
  - A new socket gets the current stats.
- [ ] **Step 2–4.** **Step 5: Commit** `feat(server): context, plan limits and cost stats`.

### M4-04: Sessions list, switch and restart

**Files:**
- Create: `server/src/sessions.ts` and its test.
- Modify: `session.ts`, `server.ts`, `fileRoutes.ts`/`git.ts`/`files.ts` (the root becomes a getter), `comments.ts` wiring, `hub.ts` (reset).

**Interfaces:**
- Produces:
```ts
export const titleOf: (x: { customTitle?: string; summary?: string; firstPrompt?: string } | null) => string | null; // first non-empty not starting with '/'
export function cwdOf(id: string, projectsDir?: string): string | null;  // ~/.claude/projects/*/<id>.jsonl head 256 KB, regex /"cwd":("(?:[^"\\]|\\.)*")/, cached incl. null
export function listSessionsView(o: { current: string | null; root: string }): Promise<{ current: string | null; root: string; sessions: { id: string; title: string; at: number; size: number; cwd: string }[] }>;
// AgentBackend gains listSessions(): Promise<{ sessionId: string; customTitle?: string; summary?: string; firstPrompt?: string; lastModified: number; fileSize: number; cwd?: string }[]>
//   and sessionInfo(id: string, dir: string): Promise<{ customTitle?: string; summary?: string; firstPrompt?: string } | null>
//   sdk: listSessions({ limit: 300 }) / getSessionInfo; fake: scripted list (e2e needs two sessions)
// GET /sessions → listSessionsView
// SessionManager.switch(o: { id: string | null; dir: string }): Promise<void>   // rejects while busy
// SessionManager.restart(): Promise<void>                                      // = switch({ id: current, dir: root })
// SessionManager.info(): { id, root, title, model }
// EventHub.reset(): void   // clears history; every socket gets { kind: 'replay', events: [] } then the new session's replay
```
- Switch flow:
  1. Refuse while busy (R-M4-4) and when `dir` is not an existing absolute directory.
  2. Close the agent and wait for its message loop to end.
  3. Set the root to the realpath of `dir`, and persist `lastSession(dir)`.
  4. Reset the hub.
  5. Start the new agent with resume and the mode taken from prefs for that dir.
  6. Replay the transcript (the existing resume path), then emit the `session` event (id, new root, title, model), `mode`, `stats` and `comments` for the new id.
- Every root-dependent route reads the root per request. The `listFiles` cache, the sources cache and the `cwdOf` cache are invalidated per root or keyed by it.
- The title comes from `getSessionInfo(id, { dir: root })` through `titleOf`. It is refreshed after each `result` and cleared on `conversation_reset`.
- `model` comes from `system/init`.
- R14: a `comments` message whose `sessionId` differs from the current one is rejected (`where:'comments'`, message "stale session").

- [ ] **Step 1: Failing tests (fake backend).**
  - `titleOf` skips `/clear` and returns the summary.
  - `cwdOf` finds the cwd in a large head and caches a miss.
  - `/sessions` drops entries without a cwd.
  - A switch to another dir: `/file` of an old-root path returns 404 or 403, `/tree` lists the new root, sockets get the replay reset and the new session event.
  - A switch while busy is rejected.
  - Restart resumes the same id.
  - A comments push carrying the old sessionId after a switch is rejected and stores nothing.
  - Two sockets both receive the reset.
- [ ] **Step 2–4.** **Step 5: Commit** `feat(server): session list and in-process switch and restart`.

- Create: `web/src/shell/TasksLine.tsx`, `web/src/tasks/slice.ts`, and their tests.

**Interfaces:**
- This follows the prototype's `onTask` and `renderTasks` exactly:
  - `task_started` adds an entry (skipped when `ambient || skip_transcript`). `desc` comes from `description`, then `subagent_type`, then `task_type`, then `'task'`. `start` is the event ts.
  - `task_progress` updates `tokens`, `tool` and `summary`.
  - `task_updated` with a status other than running, pending or paused removes the entry; otherwise it updates `desc`.
  - `task_notification` removes the entry.
  - A `replay` clears the list first.
- Each row shows `⚙` + desc and `time · fmtK(tokens) tok · tool`. Time is `Ns` under 60 s, else `m:ss`. The row tooltip is the summary.
- A 1 s tick runs only while any task is live.
- The line sits above the composer. M2 replaces it later.
